## 内核 compaction hook 契约核实（关键架构发现 · claude化 gap-fill 方向）
- `session.compacting` 返回类型 `SessionCompactingResult`（shared-events.ts:368-373）仅含 `{context?, prompt?, preserveData?}`，**无 summary 字段** → 该 hook 只能"叠加"进内核自有 LLM 压缩（作为 extraContext / promptOverride，session-maintenance.ts:801-802），**不能替换**压缩结果。当前 Tiffa gap-fill 走此 additive 路径（claude-mode-extension.ts:541-621，正则提取改文件/命令/决策行）。
- 真正"代替上下文压缩"的入口是 **`session_before_compact`**：其 `SessionBeforeCompactResult.compaction?: CompactionResult`（shared-events.ts:360-365）走内核 `kind:"fromHook"` 分支（session-maintenance.ts:764-770, 1615-1626），内核**跳过自有 LLM 压缩**、逐字采用 hook 给的 summary。
- `CompactionResult` 必须带 `firstKeptEntryId`（截断边界：此 entry 之前被总结、之后保留原文）。`session_before_compact` 事件带 `preparation`（含 messagesToSummarize + turnPrefixMessages = 完整待压缩 transcript），与 `session.compacting` 拿到的 messages 同源（session-maintenance.ts:1598-1602）。
- 风险：fromHook 路径 summary 即最终上下文，旁路 AI 丢细节无二次 LLM 兜底；compaction 又是 context overflow 的兜底恢复路径，故旁路 AI hook 必须 try/catch、失败则回退让内核自压。
- 用户今日已用 MCP 调旁路 AI 做对话重命名成功 → hook 内异步调外部 AI 通路已验证。结论：旁路 AI 总结 gap 能完全代替压缩，但入口须换 `session_before_compact`+`compaction`，非当前 `session.compacting`。
- 提议两阶段：Phase A 仅把 session.compacting 正则提取换成旁路 AI 语义总结（叠加、零风险提质）；Phase B 迁 session_before_compact 返回完整 CompactionResult（真·替换）。待用户确认走哪条。
- 备注：AGENTS.md 称 gap-fill "dump last 50 messages" 已过时；实际代码遍历全部 event.messages，仅对提取条目数设 60 上限。

## 研究：Claude Code compaction 真实机制（23:24 用户问 subagent 总结优势）
- 核心澄清：Claude compaction 是 **subagent(fork agent) 出摘要直接替换旧历史**（[boundary, summary, recent]），非两层总结。若类比 Phase A 两层则 Claude 也脱裤子，但它没。
- subagent 总结相对"主模型在已污染上下文里自己总结自己"的真实优势（5 点，均有机制出处）：
  1) 躲 context rot：autocompact 在上下文近上限时触发=模型最不聪明时刻，自总结摘要最差；fork agent 在干净窗口总结不受污染。
  2) cost/模型解耦：压缩路由便宜小模型(Haiku)且不烧主 session prompt cache；主模型自压要么 flagship 全价、要么切模型烧 cache 更贵。
  3) 独立视角减锚定/ego：fork agent 读原始 transcript，更忠实保留被推翻方案/错误/待办。
  4) 专门 9-section 结构化压缩 prompt（意图/概念/文件片段/错误修复/待办/下一步 verbatim）保召回。
  5) 异步/Tier2 Session Memory：后台 agent 持续维护摘要，压缩时零延迟零成本取用，主模型自压做不到"提前总结"。
- Claude 自己也怕 autocompact 坏时机（模型最笨时）→ 官方建议主动/定期 /compact 而非等 overflow。Phase B 设计要考虑触发时机，不止 overflow 兜底。
- 结论强化：Phase A 两层叠加确属脱裤子；Phase B(fromHook 替换)才复刻 Claude subagent 替换模式，获上述 1-4 优势。Phase B 还应抄 Claude 的 circuit breaker / PTL retry(超长时丢最旧 group 重试) / fallback 设计。

## 用户定调 Phase B 心智模型（23:32）+ 真实坏处清单
- 用户结论：用旁路 AI 干净独立窗口 + 结构化约束总结，代替主 LLM 随意/被污染的总结 = Phase B 本质。当前旁路=另起对话(同主模型)，干净点到手；省钱点到手但未达 Claude 极致(无无关上下文+无主系统提示词，但仍是旗舰全价/未路由便宜小模型)。相对旧 gap-fill：好处=能推翻主 LLM 错误(gap 仅补充)；坏处=用户原以为没有，实则如下。
- **真实坏处（4 条，Phase B 设计必须处理）**：
  1) **可靠性单点（最大真坏处）**：compaction 是 context overflow 兜底恢复路径；内核自有 LLM 总结永远可用(同引擎在跑)，旁路 AI 是外部依赖，down/慢/返回畸形 → 会话无法从 overflow 恢复 → 死循环/卡死。gap-fill additive 无此患(叠加在内核自压之上)。→ 必须 try/catch 失败回退内核自压。
  2) **firstKeptEntryId 边界成硬责任**：fromHook 内核逐字信任你的截断边界；边界推太前=丢近期 in-progress 工具态/未决结果。内核自压会小心算切点(不切 mid-turn、保留近期 verbatim)，现需自己复刻"保留最后 N 条 verbatim"。
  3) **幻觉/注入零兜底(single-pass 代价)**：两层内核有第二遍 LLM 复核；single-pass 旁路摘要成字面上下文无二次检查，旁路若编出伪决策/漏约束即静默固化进上下文，对按文件路径/决策行动的 coding agent 危险。gap-fill additive 顶多成噪声，替换型则成毒。
  4) **"能推翻"≠"会正确推翻"(同模型偏置)**：干净窗口减锚定但有限；若旁路=主模型同族，系统性推理偏差(原错误是能力型而非锚定型)会以更干净措辞重现。"能推翻"仅在错误由锚定驱动时成立，能力型错误无效。
- **成本 precision**：Claude 真省钱=路由便宜小模型(Haiku)+不烧主 session cache；旁路若用主旗舰=省上下文+系统提示词开销，但 token 按旗舰全价。想拿满 Claude 成本优势应把旁路路由到便宜/小模型(如 tiny mimo-v2.5 或本地小模型)，而非主旗舰。
- **"完全替代"的安全条件**：①稳健回退(异常→内核自压) ②正确边界(保留末 N verbatim) ③9-section 结构化 prompt ④旁路路由廉价/异模型拿成本+独立双收益 ⑤不只 overflow 触发，考虑主动/定期压缩(避 autocompact 坏时机)。
- 阶段状态：Phase B 设计就绪待落盘；用户尚未明确说"动手"，应先贴精确改动方案确认(受控文件 config/extension)。Phase A 暂留(env 门控零回归)可后续随 Phase B 上线而弃用。

## 概念澄清：边界(firstKeptEntryId) ≠ 压缩时机（23:47）
- 用户问"边界算法是不是指的压缩时机"→ 否，两不同层。
- **边界=切点位置(空间)**：firstKeptEntryId 之前被摘要替换、之后(含)原文 verbatim 保留；典型算法=保留最后 N 条(近 1-2 轮)原文、前面交旁路总结。是代码责任(原内核自算切点，现需 extension 算，填错静默丢近期工具态)。即此前说的"真硬骨头"。
- **时机=何时触发压缩**：overflow 自动(autocompact, Claude 警告的坏时机) vs 主动/手动/定期。`session_before_compact` hook 是内核决定压后才触发→只决定"怎么压(边界+质量)"，决定不了"何时压"。改时机需另起主动触发机制，不在该 hook 职责内。
- 关系：时机决定压不压/何时压；边界决定压时哪些原文存活。Phase B 硬活是边界(前者)；时机是独立、更偏内核侧的改进项(对应"主动压缩优于 overflow 兜底")。
