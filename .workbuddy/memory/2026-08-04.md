## 压缩阈值根因诊断（23:49）
- **现象**：deepseek-v4-flash 在 models.yml 配 `contextWindow: 102400`，但实测在 ~128k 才压缩。
- **阈值公式**（`pi-agent-core/src/compaction/compaction.ts`）：`shouldCompact` 阈值 = `contextWindow - max(0.15×contextWindow, reserveTokens)`（默认即 `0.85×contextWindow`）。`session-maintenance.ts:980` 直接取 `model.contextWindow` 作基准。
- **根因方向**：行为像 128k 才压 ⟹ 内核实际 `model.contextWindow` ≠ 102400，而是 ≈128000+。代码上 `modelDef.contextWindow` 是被直接采纳的（`models-config.ts:95` 校验、`666` 带入；`model-registry.ts:708` `resolvedModel.contextWindow` 优先于 catalog/兜底）。所以矛盾点二选一：
  1. **最可能：改完 models.yml 后没重启 Tiffa**，内核用启动时的旧配置（旧 deepseek-v4-flash 无 contextWindow 或 =128000 级），回退链 `resolvedModel.contextWindow ?? reference?.contextWindow ?? 128000` 落到兜底/旧值。
  2. 解析回退：catalog 内置 `deepseek/deepseek-v4-flash` 的 `contextWindow: 1048576`（provider=kilo，见 `pi-catalog/src/models.json:29921`），若用户 contextWindow 未定义且 reference 不匹配则兜底 128000。
- **用户侧最快验证**：看 Tiffa UI 底部状态栏上下文窗口数字（`footer.ts:144` 直接显示 `state.model?.contextWindow`）——显示 128K/150K 即未生效，显示 102.4K 即生效（此时阈值应在 ~87k，需重新核对"128k"的观察口径）。
- **确定性修复（推荐）**：在 `config.yml` 加 `compaction:` 组的 `thresholdTokens`（固定 token 阈值，优先级高于百分比，`compaction.ts:361-364`），例如 `thresholdTokens: 90000` 强制 90k 压缩，彻底绕开 contextWindow 解析歧义。当前 config.yml **无 compaction 组**。受控文件，改动需先确认。
