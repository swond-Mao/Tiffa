## 拖拽图片给本地多模态模型读不了（诊断）

用户现象：从对话框拖图片进去，本地多模态模型（qwen / qwen-remote，Ollama/frp 中继 llama.cpp）读不了。

### 链路
renderer 读 base64 → `tiffa:send(message, images)` → 主进程打进 `frame.images`（仅 webp→png）→ 内核 `normalizeModelContextImages` → 发给模型。

### 根因（已定位代码）
- 内核 `sdk.ts:3039-3052`：若 `activeModel.input` 不含 `"image"`，图片被替换成 `[image omitted…]` 文字。纯文本模型（mimo-v2.5 / glm-5.2 / MiniMax-M3 / deepseek 等）会命中。用户 models.yml 已正确给视觉模型加 `input:["text","image"]`，故非此因。
- 本地模型 WebP 静默崩（用户实际命中）：`image-loading.ts:16-29` 的 `modelLacksWebpSupport` 只看 provider key 是否 `ollama/llama.cpp/lm-studio/local-server`，用户 key 是 `qwen`/`qwen-remote` → 内核以为支持 webp。`resizeImage` 对 >~5MB 或超尺寸图 `excludeWebP=false` 优先编码 webp（image-resize.ts:251-259）→ llama.cpp 解不了 → 空回复。
  - fast-path：小 PNG(<5MB 且尺寸合规) 原样透传 PNG → 正常；大图/webp 源才崩。
  - **盲区**：之前 webp-crash-fix.md 的扩展 `tool_result` webp2png 只覆盖 `read` 工具路径，未覆盖拖拽 `frame.images` 路径 → 主进程虽 webp→png，内核仍可能把大 png 重编码回 webp。
- 已排除 `images.blockImages`：`agent.db` settings 表无此项（仅 skills.*）。

### 结论
小图能读、大图/某些格式静默崩。用户选择先诊断不动文件。

### 后续可选修复（均未落地，待确认）
1. `OMP_NO_WEBP=1` 加进启动环境：最稳，全模型走 PNG，覆盖拖拽+read 两条路径；代价云端失去 webp 压缩（功能无影响）。
2. 扩展 `input` 钩子补 webp→png：只拦本地 provider，贴合现有架构，需改 claude-mode-extension.ts。
3. 改 provider key 为 ollama/llama.cpp：让内核自动排除 webp（动 models.yml，影响其他逻辑）。

## WebP 白名单（反向过滤）改造复查 — 结论：机制在跑，但三处失效

用户此前把 webp 处理改成"白名单 + 反向过滤"（云端放行 webp，本地转 PNG）。复查实现是否生效。

### 实现现状（claude-mode-extension.ts v6.2）
- L149-177：`LOCAL_ENGINE_BLACKLIST` + `loadUserProviders()`（自己 readFileSync + 正则 parse models.yml，绕过内核 schema 剥离）+ `webpBlockToPng()`（Bun.Image）。
- L255-259：`session_start` 加载白名单并打日志。
- L781-804：`tool_result` 钩子内做转换判断，`provider = ctx?.model?.provider || currentModelProvider`（L281-282 在 before_agent_start 赋值兜底）。
- 判定逻辑：本地引擎黑名单命中 → 转；models.yml 有该 provider 且未标 supportsWebp → 转；不在 models.yml（内置云端）→ 放行。

### 三处失效（均有实证）
1. **白名单为空 → 退化成全黑名单**。models.yml 里 0 个 `supportsWebp: true`。日志实证：
   `[webp_whitelist.loaded] user providers: kimi,xiaomi,qwen,qwen-remote,volcengine,opencode-zen,minimax,deepseek | webp-ok: (none)`
   → 8 个 provider 全部落入转换分支，"反向过滤/云端放行"设计意图未实现。日志另见 `tool_result.webp2png provider=minimax`（云端也在转）。方向偏保守，不致错，仅多耗 CPU。
2. **拦截点只挂 `tool_result` → 拖拽路径零覆盖**（致命，即用户拖图崩的直接原因）。拖拽图是用户消息 content block，走 `frame.images` 直达内核，不产生 tool_result 事件。
3. **内核会把扩展转出的 PNG 再编码回 WebP**（致命）。`image-loading.ts:114-134` `normalizeModelContextImages` 对每张图无条件 `resizeImage(image, resize)`；qwen/qwen-remote 不在内核 `modelLacksWebpSupport` 名单 → `resize` 为 undefined → `image-resize.ts:164` `excludeWebP = options?.excludeWebP ?? isWebPExcluded()` fallback env → 未设 `OMP_NO_WEBP` 时为 false → 大图重编码候选含 webp（L251/L278）。扩展努力被内核抵消。
   - 注：`loadImageInput`(L160) 的 `shouldReencodeWebP` 只在源本身是 webp 时触发，但 `normalizeModelContextImages` 是无条件调 resizeImage，两者不同，别混。

### 次要 bug
`tool_result` L771-778：读 `skill://` 命中 SKILL_PATH_HINTS 时提前 `return`，会跳过后面的 webp 转换。当前不涉及图片，无实害，但属逻辑顺序缺陷（webp 检查应前置或合并）。

### 推荐修法（未落盘，待用户确认）
`OMP_NO_WEBP=1` 仍是最优解：一次性同时解决失效点 2 和 3（内核层全局兜底，拖拽+read 全覆盖），且不必再依赖扩展白名单。扩展白名单可保留作云端优化，但需在 models.yml 给云端 provider 补 `supportsWebp: true` 才有意义。

## supportsTools 错标修正 + 文档清理（已落盘 ✅）

```ts
if (format === "auto") {
  if (model?.supportsTools !== false) return undefined;   // undefined = 原生 function calling
  const preferred = preferredDialect(model.id);
  return preferred === FALLBACK_DIALECT ? "glm" : preferred;
}
```

## 自适应滚动跟随（Electron 前端，2026-08-01）

需求：默认视窗跟着新对话下滚；用户一旦向上滚轮 / 拖滚动条就交出控制权（视窗跟手）；有一个按钮一键回到底部；下一轮新对话自动恢复跟随。

### 根因（原实现为什么会"跟丢"）
`styles.css` 里 `.messages` 带 `scroll-behavior: smooth`，而流式输出时每个 token 都调一次 `scrollToBottom()` 写 `scrollTop`。平滑动画被反复打断、永远追不上还在增长的 `scrollHeight`；一旦落后超过原代码里的 80px `nearBottom` 阈值，判定就永久失效 → 表现为"自己停住不跟了"。
**修复思路**：把"是否跟随"与"距底距离"解耦——跟随态只由**用户显式意图**（上滚轮 / 拖滚动条 / PageUp·Home / 触摸上滑 / 拖 minimap）翻转，程序滚动一律强制 instant（临时 `el.style.scrollBehavior='auto'` 再还原），绕开 smooth 滞后。

### 落盘改动（3 文件）
1. `electron/renderer/app.js`（→5824 行）
   - 新增 `followScroll` 控制器（紧跟 `minimap` 对象之后）：三态机 follow / free / reset；`RESUME_EPS=4`（距底≤4px 视为到底，自动恢复跟随）、`BTN_SHOW=80`（脱离跟随且距底>80px 才显示按钮）；rAF 节流的 `schedule/tick`；`MutationObserver` + `load`(capture，图片撑高) + `ResizeObserver` 三路触发。
   - `scrollToBottom(force)` 重写为薄壳：`force→followScroll.attach()`，否则 `schedule()`。**约 30 处旧调用点零改动自动获得新行为**。
   - 钩子：`init()` 里 `followScroll.init()`；`minimap.jump()` 末尾 `detach()`；`sendMessage()` 渲染用户消息处 `scrollToBottom()` → `followScroll.reset()`；4 处会话恢复 `scrollTop = cached.scrollPos` 之后补 `followScroll.sync()`（避免切回历史中段被拽到底）。
2. `electron/renderer/styles.css`（→3909 行）：新增 `#scrollToBottomBtn`（`right:26px` 避开 minimap，圆形悬浮、`.visible` 淡入、`.has-new::after` 小红点表示 agent 仍在输出）。
3. `electron/renderer/index.html`：仅确认 `#chatPanel` 为 `position:relative` 容器，按钮由 JS 动态插入，未改文件。

### 验证
Bun Transpiler 语法通过；styles.css 花括号平衡；写 mock-DOM 抽出真实 `followScroll` 代码块跑 8 场景 15 断言全过（默认跟随+增长、上滚交权、红点、手动滚回底恢复、20px 微滚不误判到底、点按钮、新消息 reset、切会话到历史中段）。

## 添加模型供应商后「拉取失败」+ 不进分组栏（Electron 前端，2026-08-01）

### 用户现象
设置里加新供应商 → 点「保存并获取模型列表」→ 显示拉取失败；重启后供应商已存在（但无模型），此时拉取才成功。且新供应商不出现在下面模型切换器的供应商分组里。

2. **向导只写白名单不写模型**：原 `onFinish` 只把选中模型写进 `enabledModels` 白名单（仅过滤显示），没写进 `models.yml` 的 `provider.models`。即便实例重载，没有模型条目也选不到 / 不进分组。

### 落盘改动（`electron/renderer/app.js`）

- `onFinish`：除白名单外，把选中模型 `id` 写进 `models.yml`（`writeTiffaProvider` 带 `models` 列表），内核重载后真正可用。
- 新增 `applyModelsConfigChange()`：写盘后若 `state.agentRunning` 为 false 则 `restartTiffa()`（= 主进程 `models:restart`，closeAll+activate 各 cwd，activate 会等 ready）让实例重新读盘；否则提示重启后生效。写完刷新 `loadModelConfig()` + `loadModelSwitcherList()`。
- 在 `onSaveOnly`、`createProviderCard` 的删除/「从服务器拉取模型」确认、`addModelDialog` 提交 4 处均补调 `applyModelsConfigChange()`，使模型变更即时生效，不再需要手动点「重启」。

### 验证
`node --check app.js` 通过。`models:restart` 已存在且被「重启」按钮复用，重载后即可用新供应商（与现有设计意图一致）。

## Computer Use v2：运行期能不能动鼠标（实测结论，2026-08-01）

用户问「用的时候是不是不能乱动鼠标」。实测链路后结论：**鼠标位置本身几乎无害，真正的杀手是焦点切换与窗口层叠**。

- **L1（UIA Pattern 直调）完全免疫**：实测对「系统托盘溢出窗口」（非前台、平时隐藏）依然枚举出 5 个 Button 且 `invoke` 可用。UIA 走跨进程 COM，不看鼠标、不要求前台、不要求可见，窗口最小化/被遮挡都能操作。
- **L2（`_click_point` → pyautogui）抢鼠标**：瞬移+点击，用户同时拖拽会打架，点完鼠标停在目标处不归位。
- **L3（`grab` → mss）**：基于 BitBlt/DXGI，**不合成光标层**，截图里没有鼠标指针；但抓的是屏幕矩形区域（非 PrintWindow），**被别的窗口压住会把遮挡物拍进去**。
- **L4 / `set_text` 键盘降级路径最危险**：`pyautogui.hotkey('ctrl','a') + typewrite` 打进**当前焦点**，用户中途切窗口 → 文字打到用户那边。
- **`inspect(window=None)` 默认取前台窗口**（`get_foreground()`），用户点了别的窗口就会枚举错对象。

**加固可用的三个 API（已实测可用）**：`GetAsyncKeyState`（检测用户正在按键/拖拽，抢鼠标前避让）、`iuia.GetFocusedElement()`（打字前校验焦点确实在目标元素上，不匹配就拒绝而非盲打）、`GetLastInputInfo`（用户空闲时长）。另可在 `_click_point` 前后 `GetCursorPos`/`SetCursorPos` 保存并恢复鼠标位置。**尚未实施，待用户确认是否加固。**

## Computer Use v2：OCR 文本识别层（L5，2026-08-01）

用户反馈：Ctrl+F 能搜微信，真正瓶颈是**截图太密、模型看不清文字**。于是加 L5 OCR 兜底——不依赖控件树，直接对像素做文字识别+定位，专治微信(Qt 5.15, UIA 全盲)这类窗口。

### OCR 选型与坑
- **WinRT `winrt-Windows.Media.Ocr`**（系统自带，zh-Hans-CN 语言包预装）为最终方案。`winsdk` pip 装不上（缺 skbuild 源码构建），改 `winrt-*` 预编译 wheel。
- **异步坑（关键）**：`OcrEngine.recognize_async(sb)` 返回的是 `_IAsyncOperation` 对象，**不是 coroutine**，直接 `asyncio.run(eng.recognize_async(sb))` 报 `ValueError: a coroutine was expected`。必须包一层 `async def _go(): return await eng.recognize_async(sb)` 再 `asyncio.run(_go())`。
- **PIL→SoftwareBitmap**：用 `Buffer` + `memoryview` 零拷贝（3ms/2.3MB）。`SoftwareBitmap` 无静态 `create_copy_from_buffer`，要用构造器 `SoftwareBitmap(BGRA8,w,h,PREMIULTIPLIED)` + 实例 `copy_from_buffer(buf)`。`winrt.windows.security.CryptographicBuffer` 模块不存在，已弃用。
- **OcrLine 无包围盒**：`OcrLine` 只有 `text`/`words`；`OcrWord` 才有 `bounding_rect`(x,y,width,height)。所以行包围盒 = 各 word 包围盒并集。

### 落盘改动（2 文件）
1. **`skills/computer-use/uia_core.py`**：新增 L5 OCR 段（截图函数之后）。
   - `_pil_to_software_bitmap(img)` / `_get_ocr_engine()`(缓存) / `_ocr_run(sb)`(async 包装) / `_union_line_rect(words)`。
   - `ocr_region(window, region, min_width=720, max_pixels=None)`：OCR 指定区域，返回带**物理屏幕坐标**的文本行（已叠加 offset、按 scale 还原）。与 screenshot 分工——OCR 默认**不缩放**（保像素密度），小区域反而 `min_width` 上采样。
   - `find_text(query, ..., threshold=0.45, return_all=False)`：OCR + `difflib` 模糊匹配（子串命中=1.0，否则 SequenceMatcher ratio），返回最佳命中物理中心坐标。容忍中英文混输/拼音/OCR 错别字。
   - `click_text(query, ..., verify_title=None)`：OCR 找文本→`_click_point` 中心；若给 `verify_title` 则点后截图 OCR 校验标题栏（region="titlebar"），未命中返回告警字符串。
2. **`skills/computer-use/computer_use_mcp.py`**：tools/list 增至 8 个，新增 3 个 OCR 工具 + `ui_screenshot` 加 `region`/`region_rect`/`min_width` 参数（让模型能请求裁剪+放大的局部图，直接降密度）。
   - `ui_ocr`：OCR 区域→文本行表（cy/cx/包围盒），模型只读字即可定位。
   - `ui_find_text`：OCR 模糊匹配→返回最佳命中坐标（解决"点错群"）。
   - `ui_click_text`：OCR 找字并点击，可选 `verify_title` 校验。

### 验证
- `ocr_region` 经 monkeypatch screenshot 喂 wx-list.png 端到端跑通：返回 24 行、坐标正确（offset 33,3 还原）、`find_text("病历评审")` 命中 score 1.0、不匹配查询返回 None。

- 三个 .py 文件 `py_compile` 全通过。

### send_agent_verify.py 重写（修复"发错群"）

### scope 分类限定——从"微信专用"泛化为通用机制（用户质问后修正）
用户点出：之前 `scope` 写死微信搜索标题(群聊/联系人/聊天记录/公众号)，只对微信有效。已泛化：
- `_scope_lines(lines, scope, scope_end=None)`：把 OCR 行限制在「某标题行 ~ 下一个标题行」之间。`scope` 可以是：
  - `"any"/None` 整区（通用）；
  - 预设 `group/contact/chat_history/official`（内置微信中文标题，4 个兄弟标题都已知→边界自动算）；
  - **任意标题文字**（如 `"Results"`/`"歌曲"`/`"群聊"`）——把它当标题去定位区块。
- `scope_end`（可选）：多分类 app（如英文 Results/Suggestions）务必与 scope 成对传。否则后续分类标题不在已知表里→匹配越界到下一区块（实测翻车：scope="Results" 漏掉 end 会误命中 Suggestions 里的行）。模型应先 `ui_ocr` 看清有哪些标题再传。
- `_norm` 加 `unicodedata` 去声调/变音符号（OCR 常把 jian 读成 jiàn）；评分改「整行==目标=1.0 否则 difflib ratio」，整名匹配恒高于子串，避免两个同名群时点错长的那个。默认 `threshold` 0.45→0.5，过滤聊天记录长句误中。
- `find_text`/`click_text` 均加 `scope_end` 形参；MCP `ui_find_text`/`ui_click_text` schema 增 `scope`(自由串，非 enum)+`scope_end`；SKILL.md 注明通用性。
- 实测：英文 app `scope="Results",scope_end="Suggestions"`→命中 Results 内行(cy110)，不泄漏；微信 `scope="group"`→命中精确群行。两者均通过。
- **结论**：OCR 引擎本体(ocr_region/find_text/click_text)本就全通用(任意盲窗/应用)；只有"分类限定"原先偏微信，现已通用。`send_agent_verify.py` 仍是微信专用脚本（本质就是发微信消息），其 `scope="group"` 走预设、兄弟标题已知，无需 scope_end。

### 关键踩坑：GCM 在沙箱里拿不到凭据 → 用 wincred 覆盖
`git push` 报 `could not read Username for 'https://gitee.com'` + `/dev/tty: No such device`。根因：全局 `credential.helper` 链是 `helper-selector` → `git-credential-manager.exe`，GCM 在无 tty/无 GUI 的环境下走交互分支失败（还留下 `PortableGit/etc/gitconfig.lock` 陈旧锁）。
凭据其实**已存在** Windows 凭据管理器（`cmdkey /list` 可见 `LegacyGeneric:target=git:https://gitee.com` 与 `...gitcode.com`），只是 GCM 读不出来。

**解法（每命令覆盖，不改全局配置）**：
```bash
git -c credential.helper= -c credential.helper=wincred push origin master
```
先用空值清掉继承的 helper 链，再指定 `wincred`（PortableGit 自带 `git-credential-wincred.exe`）。验证方式：
`printf 'protocol=https\nhost=gitee.com\n\n' | git -c credential.helper= -c credential.helper=wincred credential fill`

另：`git push` 前若见 `could not lock config file .../gitconfig: File exists`，删掉 `gitconfig.lock` 再试。
