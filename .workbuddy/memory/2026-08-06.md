## Git 远端被切成 SSH 导致推送失败（重要坑）

- 现象：本机 `git remote -v` 显示 origin / gitcode 均为 **SSH**（`git@gitee.com:...` / `git@gitcode.com:...`），`git push` 报 `Host key verification failed`（SSH host key 未信任）。但 2026-08-02 推送时远端还是 **HTTPS**（`https://gitee.com/mao-yihong/oh-my-tiffa.git`），走 wincred 凭据正常。
- 修复：`git remote set-url origin https://gitee.com/mao-yihong/oh-my-tiffa.git` + 同理 gitcode 改回 HTTPS，再 `git -c credential.helper= -c credential.helper=wincred push`。推送恢复正常。
- **结论**：本仓库推送的可靠姿势仍是 **HTTPS + wincred**（Aug 2 也验证过）。若以后又变 SSH 推不动，先 `git remote -v` 确认协议，再切回 HTTPS。SSH 失败的根因是 known_hosts 未收录 gitee/gitcode 主机密钥，不是凭据问题。

## deepseek-v4-flash 频繁压缩对话诊断

- 现象：用户把 deepseek-v4-flash 的 contextWindow 从 102400 改到 1048576（文件已改），但压缩仍频繁，怀疑数值不生效。
- 压缩触发真相：`shouldCompact(contextTokens, contextWindow, settings)`（`pi-agent-core/src/compaction/compaction.ts:334`）= `contextTokens > contextWindow - reserveTokens`。`DEFAULT_COMPACTION_SETTINGS`（`compaction.ts:205`）里 `thresholdPercent/thresholdTokens` 均为 `-1`，reserve 默认 `16384`。所以 **1M 窗口时阈值 ≈ 103 万 token，绝不频繁触发**。
- 用户实际用的是 `deepseek/deepseek-v4-flash`（会话 JSONL `model_change` + `provider:"deepseek"` 实锤），改的是对的模型，非 opencode-zen 的 `deepseek-v4-flash-free`（200000）。
- 排除 discovery 覆盖：deepseek 是 `openai-completions` 且 models.yml 无 `discovery.type`，不在 `discoverableProviders`（仅 ollama/llama.cpp/lm-studio/openai-models-list/litellm/proxy），`model-discovery.ts` 的 API `context_length` 覆盖路径不跑。
- 排除解析 bug：自定义模型 `contextWindow` 直接从 `modelDef.contextWindow` 读取（`model-registry.ts:666`）。
- **根因 = 内核不热加载 models.yml**：`model-registry.ts` 无 fs.watch/reload，models.yml 是内核子进程启动时一次性加载。改文件后若未彻底退出并重开 tiffa-desktop.exe（含托盘），内核仍用旧值 102400 → 阈值 ~87k → coding 对话几轮即压缩，表现"改成1M仍频繁"。
- 附带线索：deepseek-v4-flash 会话 JSONL 里 `usage` 全为 0（input/output/totalTokens=0），provider 不报 token 用量 → `shouldCompact` 的 `providerContextTokens=0`，压缩决策**完全依赖本地 `estimateTokens` 估算**；且该模型 `supportsTools:false` → GLM in-band 文本协议，工具调用变文本塞进上下文。
- 验证/修复：彻底退出 Tiffa（含托盘）再重开，让内核子进程重载 models.yml；若重启后仍频繁，再查本地 estimateTokens 对该模型是否异常高估。

## 跨机器（移动硬盘盘符变化）会话不连续 — 修复落地

- 真凶（前段已定位）：会话目录名绑定 cwd 盘符（`--E--Tiffa-workspace-项目--`），换机器盘符变→B 进度写进 `--G--…--`，A 只读 `--E--…--`，两份独立文件互不合并。前端 SSE 缓存只是表象，已证伪。
- 方案：稳定 id 方案（用户确认）。内核 `--session-dir` 是唯一逃逸口（`dist/cli.js` 不可改，只能靠 flag/cwd 影响）。
- **已改 `electron/main.js`（未 commit）**：
  1. 新增 `stableSessionDirName(cwd)`：workspace 项目返回 `--wks-<suffix>--`（suffix=workspace/ 之后相对路径，盘符无关）；外部文件夹退回原 `_encodeSessionDirName`。
  2. `_findSessionFile` 改用 `stableSessionDirName` + 跨目录兜底扫描（按 UUID 匹配，防丢）。
  3. IPC 侧 `encodeSessionDirName` 委托 `stableSessionDirName`（覆盖 listProjects/listSessions/ensureProjectInJson/迁移/删除/归档等所有调用点）。
  4. **spawn 内核处（~234 行）新增** `args.push('--session-dir', path.join(_SESSIONS_DIR, stableSessionDirName(this.cwd)))` —— 内核把所有会话（新建/续接）写进 `--wks-…--`。
- **内核侧已核（无需改）**：`createSessionManager` 在「仅给 --session-dir 无 --continue」时走 `SessionManager.create(cwd, sessionDir)` → `#sessionDir=--wks-`；`moveTo` 在显式传入 sessionDir 时 `nextSessionDir=sessionDir`（不会回退 cwd 编码）；`resolveResumableSession`/`continueRecent`/`listSessions` 都用传入的 sessionDir 扫描。所以 `--wks-` 全链路稳定。
- **迁移由现有 `migrateSessionDirsForNewRoot()`（启动时无条件调用）承担**：因 `encodeSessionDirName` 已委托，步骤2 会把旧 `--E--…--`/`--G--…--` 重命名（或合并）进 `--wks-…--`，盘符不同也映射到同一目录→自动连续，不删数据。
- 校验：`node --check main.js` 通过。
- **待用户验证**：重启 Tiffa（含托盘）后，A↔B 切换同一项目，确认历史对话连续、不回退到旧状态。仍未 commit（按约定不自动提交）。
- 注意：header 内 `cwd` 字段会随实际盘符浮动（A 写 E:\、B 写 G:\），但**目录名稳定不受影响**；正常 Tiffa rpc-ui 走 switch_session（不触发 moveTo），无 cwd 改写。
