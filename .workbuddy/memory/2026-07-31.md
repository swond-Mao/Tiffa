## 排查：弱智模型测试项目对话"静默崩溃"（已定位根因，含首次误判修正）

**会话**：`sessions/--E--Tiffa-workspace-弱智模型测试--/2026-07-31T02-26-58...019fb5ff.jsonl`
**实际模型**：`qwen-remote/localmodel`（`http://47.108.197.247:9876/v1`，frp 中继到家里 llama.cpp b10066，GGUF = Qwen3.6-35B-A3B LynnStyle）。session-model-map.json 里查不到，须从 jsonl 的 `message.provider` 字段读。

### 根因：llama.cpp 的 stb_image 不支持 WebP，但错误码是 HTTP 200

链条：
1. 模型 `read` 图片 → 内核 resize 管线默认把图转成 **WebP**（省 token）
2. 发给 llama.cpp → stb_image 编译时不带 libwebp → 解码失败
3. llama.cpp 返回 **HTTP 200** + body `{"error":{"code":400,"message":"Failed to load image or audio file"}}`
4. 内核只看 status 200 → 解析 `choices` 拿不到 → 空 assistant 消息、`usage` 全 0、`stopReason=stop`
5. 重试 4 次全同样结果 → `session_stop reason=interrupted`
6. **不是 error → 扩展 error 续行不触发、UI 零报错 = "静默"**
7. 图片留在历史 → 会话永久污染，之后每次「继续」都重演 4 连空

**指纹**（下次一眼认出）：assistant `content:[]` + `usage` 全 0 + `duration` 300-450ms + `stopReason=stop` + 4 条共享同一 parentId。350ms 是纯网络往返，说明请求压根没进模型。

**复现验证**（curl/urllib 直打端点）：
- WebP → HTTP 200 / 0.30s / choices=0 / body 是 error 对象 ✅ 完全吻合
- PNG 单张 → 200 / 0.98s / prompt_tokens=1003 正常
- PNG ×5（5.79MB，含 tool-role 消息）→ 200 / 2.43s / prompt_tokens=2983 正常
→ 排除"图片太大""多模态不支持""tool 消息畸形"等假设。

### 内核其实内置了这个防护，只是没命中

`cli.js` `kJ3()`（= `modelLacksWebpSupport`，types/utils/image-loading.d.ts 有原文注释确认此 bug）：
```js
model.imageInputDecoder==="stb" || provider∈{ollama,ollama-cloud,llama.cpp,lm-studio,local-server} || api==="ollama-chat"
```
我们的 provider 叫 `qwen`/`qwen-remote`、api 是 `openai-completions` → **全部逃过检测**。内核只在自动发现 ollama/llama.cpp/lm-studio 时才自动打 `imageInputDecoder:"stb"`，手写 models.yml 不会。

### 两个修复方案（已交用户决策，按惯例改 models.yml 前需贴全文确认）

- **A（精准）**：models.yml 给 `qwen` + `qwen-remote` 的 localmodel 加 `imageInputDecoder: "stb"` → 内核自动改 PNG/JPEG。风险：手写 yaml 该字段是否被 schema 保留未 100% 验证。
- **B（保底，零风险）**：环境变量 `OMP_NO_WEBP=1`（`FA5()` 直接读 `Bun.env`，无条件生效）。代价：全局所有模型都不用 webp，图片体积略增。

### 附带发现（待处理）

- `qwen-remote` 声明 `supportsTools: false`，但会话里工具调用一直正常工作 → 配置疏忽，`qwen` 那条是 true。建议改回 true。
- 该 GGUF 是 reasoning 模型：正常回复时 `content` 常为空、内容全在 `reasoning_content`，但 models.yml 声明 `reasoning: false`。目前内核能正确映射成 thinking block，暂未致命，但声明与实际不符。

## 修复落地：扩展层 WebP 白名单（方案 C，已落盘编译验证）

### 为什么 A/B 都被否

- **A（models.yml 加 imageInputDecoder:"stb"）已验证失败**：`omp models --json` 显示 model keys 是固定白名单 `['provider','id','selector','name','contextWindow','maxTokens','reasoning','thinking','input','cost']`，**手写 imageInputDecoder 被内核 schema 静默剥离**（kJ3 读 `model.imageInputDecoder` 拿到 undefined，不命中）。改了等于没改，但不破坏（schema 是 strip 非 strict，不报 validation failed）。
- **B（OMP_NO_WEBP=1）确认对 read 生效但无白名单豁免**：关键发现 `Tw(model)` 定义是 `kJ3(W)?!0:void 0`——非黑名单模型返回 **undefined**（不是 false），而 `OY()` 内部 `Y?.excludeWebP ?? FA5()`，`undefined ?? FA5()` fallback 到 env。所以 OMP_NO_WEBP=1 能让所有非黑名单模型转 PNG。但**全局生效，云端也失去 webp 压缩**，用户要白名单豁免 → 不满足。

### 最终方案：扩展层白名单（claude-mode-extension.ts）

技术前提全部验证通过：
1. `createContext()` 返回的 context 带 `get model(){...}`（当前活动模型）——扩展 hook 第二参数能拿 `ctx.model.provider`
2. `emitToolResult` 确认传 `(event, context)` 且 `J.content!==void 0 → Z.content=J.content`（能改 image block）
3. 扩展自己 `readFileSync` models.yml parse（绕过内核 schema），Bun.Image 能 webp→PNG

**白名单策略（供应商级）**：
- `LOCAL_ENGINE_BLACKLIST`（llama.cpp/ollama/ollama-cloud/lm-studio/local-server）→ 转 PNG
- models.yml 里标了 `supportsWebp: true` 的 provider → 放行
- models.yml 里没标的 provider（用户手加本地/陌生）→ 转 PNG（安全默认）
- **不在 models.yml 的 provider（内置几十个云端）→ 自动放行**（云端支持 webp）

这样几十个内置云端自动进白名单，不用逐个列；用户手加的本地（qwen/qwen-remote）在 models.yml 没标 → 转 PNG。

### 落盘改动

- **models.yml**：撤回之前加的 `imageInputDecoder:"stb"`（无效）；给 kimi/xiaomi/volcengine/opencode-zen/minimax 5 个云端 provider 加 `supportsWebp: true`（provider 级）。`omp models` 验证校验通过、providers 正常在列。
- **claude-mode-extension.ts**（5 处）：

- **bun build 编译通过**（34.1KB bundle，无语法错误）。
